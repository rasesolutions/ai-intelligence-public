# Public-content security and withdrawal

This repository mirrors only the website's approved public feed. The website remains authoritative for publication and indexing eligibility. The mirror does not read the editorial database, private research, subscriber records or administrative APIs, and it must not introduce credentials for those systems.

## Publication safeguards

The validator keeps a strict field allowlist, canonical article and source URL checks, and separate event, profile-publication and capture dates. Accepted free-text fields are also checked for recognizable credentials, personal information, internal paths and private-material patterns. These checks are a precaution, not proof that arbitrary text is safe. A flagged feed fails as a whole before publication; resolve the issue at the authoritative source and rerun validation rather than silently deleting evidence or weakening the checks.

Code, validation policy and workflow changes go through a pull request and the owner's approval. The approved refresh can continue publishing the two validated data files together without a separate editorial approval for each already-public record. Its staging allowlist is limited to `data/latest.json` and `data/manifest.json`. Keep Actions permissions scoped to the job's needs; use the existing short-lived GitHub token rather than adding a personal token or hosting credentials.

Report a suspected exposure privately to the repository owner through an existing private channel. Include only safe identifiers: repository path, affected commit hashes, public record ID where appropriate, time window and exposure category. Do not paste the exposed value, personal details or full payload into public issues, PR descriptions, workflow output or incident summaries.

## Emergency withdrawal

1. **Stop republishing.** Pause the existing Rase publishing task's snapshot dispatch and disable **Refresh public feed** in this repository. Cancel any in-progress or queued refresh runs. Record the pause time and workflow run IDs privately, and check whether a run committed while being stopped. Keep the pause in place until the source and snapshot are verified safe.
2. **Contain credentials immediately.** If an actual credential was exposed, its owner must revoke or rotate it through the issuing service before waiting for content or history cleanup. Removing a visible file does not invalidate a credential. Do not put the replacement in this repository or create new credentials for the snapshot process.
3. **Correct the authoritative source.** Use the website's existing editorial controls to correct or withdraw the affected public material. Preserve original evidence and audit history privately. Verify the public feed itself no longer serves the sensitive content; do not repair the mirror by importing private database exports or bypassing publication eligibility checks.
4. **Replace the current snapshot.** Regenerate the complete validated feed and matching manifest from the safe public source while automatic refresh is paused. Run the regression tests against that safe pair, then publish it through a reviewed change. A previous unsafe snapshot may fail the new checks; regenerate it rather than disabling those checks. Use a normal commit, not a revert that restores an older unsafe snapshot. Verify the current `main` files and content hash through the connected GitHub reader, along with the website feed. Check for related exposure in public diffs, comments and Actions logs or artifacts; an authorized maintainer must address those copies too.
5. **Assess retained copies separately.** A new commit removes material only from the current snapshot. Old commits, tags, PR references, forks, clones, raw-file caches, search indexes and copies already downloaded can retain it. History rewriting or deletion requires a separately approved repository-administrator plan, with collaborator coordination to prevent reintroduction and account for changed commit hashes. Consult [GitHub's sensitive-data removal procedure](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository). GitHub Support can assess eligible sensitive-data cases and cached references; it does not guarantee removal of ordinary editorial content. Contact fork owners and relevant external cache/search providers through authorized channels when needed. The repository owner cannot guarantee deletion of third-party copies.
6. **Verify and resume.** Record redacted remediation evidence, source and snapshot checks, residual-copy risks, and any pending administrator or provider action. Add a regression test using synthetic material that cannot function as a real credential. After owner review, re-enable the workflow and snapshot dispatch, follow the first refresh to completion and verify its exact saved commit. Retain the incident record privately without duplicating the exposed data.

Ordinary refreshes must never rewrite history or force-push. Emergency history cleanup is an exceptional, separately authorized operation; this procedure does not authorize it automatically.
